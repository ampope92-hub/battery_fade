We lease battery packs to delivery fleets and I need a capacity estimate for the packs still out in the field, so we can plan replacements before customers start complaining about range. `/app/data/train.csv` is our teardown cohort — packs we pulled and bench-tested, so the measured `capacity_pct` is on the row. `/app/data/test_features.csv` is the field fleet, same columns, no teardown. `/app/data/README.md` describes the columns and how the two cohorts were pulled together.

Our tooling is Rust, so this has to live there — there's a Cargo project started for you at `/app/predictor` with `smartcore` and `csv` already wired into `Cargo.toml`. Fill in `src/main.rs` so that running it reads both CSVs, fits whatever model you think will hold up, and writes `/app/predictions.csv` with exactly two columns, `pack_id` and `capacity_pct` — one row for every `pack_id` in `test_features.csv`, header included, any order. `capacity_pct` is a percentage of nameplate capacity, same units as the training column. The box is offline: the crates already in `Cargo.toml` are cached locally at the versions pinned in `Cargo.lock` so builds work, but you can't pull in new ones.

About the grading: we delete whatever `predictions.csv` is sitting there, run `cargo run --release` in `/app/predictor` ourselves, and score the file that comes out — so it has to work from a clean build. We're tearing down a sample of the field packs next quarter, and your numbers get scored against those bench results: the R² has to reach at least **0.88** to be worth planning around. Fair warning, the last vendor we tried this with handed us a model that looked excellent in cross-validation and was useless on the actual field packs, so the bar is checked on the bench results and nothing else.
