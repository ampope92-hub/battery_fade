We lease battery packs to delivery fleets, and I want a capacity number for every pack still out in the field so we can schedule replacements before the range complaints start. `/app/data/train.csv` is the teardown cohort, packs we pulled and bench-tested, so capacity_pct is filled in on those rows. `/app/data/test_features.csv` is the fleet still running: same columns, no capacity. There's a README next to them in `/app/data` covering what each column means and how the two cohorts were put together.

We're a Rust shop, so build it in Rust. `/app/predictor` is a Cargo project with smartcore and csv already in Cargo.toml; put your work in `/app/predictor/src/main.rs`. Running it should read both CSVs, fit whatever holds up, and write `/app/predictions.csv` with two columns, pack_id and capacity_pct, one row per pack in test_features.csv, header included, order doesn't matter. capacity_pct is percent of nameplate, same units as the training column. There's no network on this box, so you're stuck with the crates already in Cargo.toml at their Cargo.lock versions.

On grading: we bin whatever predictions.csv is sitting there, run cargo run --release in `/app/predictor` ourselves, and score what comes out, so it has to work from a clean build. A sample of the field packs goes to teardown next quarter and your numbers get scored against those bench results. R² of 0.88 or better or it's not worth planning around. Last vendor we tried this with handed us a model with beautiful cross-validation numbers that was useless on the actual field packs, so the bench results are the only thing being checked.
