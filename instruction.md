We lease battery packs to delivery fleets, and I want a capacity number for every pack still out in the field so we can schedule replacements before the range complaints start. `/app/data/train.csv` is the teardown cohort, packs we pulled and bench-tested, so capacity_pct is filled in on those rows. `/app/data/test_features.csv` is the fleet still running: same columns, no capacity. There's a README next to them in `/app/data` covering what each column means and how the two cohorts were put together.

We're a Rust shop, so build it in Rust. `/app/predictor` is a Cargo project with smartcore and csv already in Cargo.toml; put your work in `/app/predictor/src/main.rs`. Running it should read both CSVs and write `/app/predictions.csv` with three columns — pack_id, capacity_pct, replace_cycle — one row per pack in test_features.csv, header included, order doesn't matter. capacity_pct is percent of nameplate, same units as the training column, so it has to come out between 0 and 100 — a pack can't hold more than it shipped with, and anything outside that isn't a capacity we can act on. replace_cycle is the number that goes on the work order: the cycle count at which that pack gets pulled off the van, read off the same odometer as the cycles column in the export, so it counts from new and not from today. Our lease contracts call a pack finished at 80% of nameplate and the entire point of scheduling the pull is to get there before it does, so across the packs you're scheduling I want no more than about one in ten to be under 80% already by the time its number comes up. There's no network on this box, so you're stuck with the crates already in Cargo.toml at their Cargo.lock versions.

On grading: we bin whatever predictions.csv is sitting there, run cargo run --release in `/app/predictor` ourselves, and score what comes out, so it has to work from a clean build. These packs have since been run on long enough that we know both numbers for real — what each one benched at, and the cycle count where it actually dropped through 80%. capacity_pct is scored against the bench results and needs R² of 0.55 or better. replace_cycle is scored on how many packs were already under 80% when your number came up: fleet-wide that share has to land between 7% and 13.5%, and we run the same count inside each third of the batch by fast-charge share, where every third has to land between 6% and 14.5%. A schedule that only comes out right averaged over the whole fleet is one I can't hand to the depots — the vans that live on the fast charger are the ones the complaints come from. Last vendor we tried this with handed us a model with beautiful cross-validation numbers that was useless on the actual field packs, so what happened to these packs is the only thing being checked.
